# f3s infrastructure audit — 2026-09-25

Read-only audit of the f3s homelab. Nothing was changed. Findings come from live
checks against f0–f3, r0/r2, pi0–pi3, rocky, blowfish/fishfinger, the k3s API
and public endpoints, plus the conf repo, unless marked otherwise.

## Critical — act now

1. **f1 (and so r1) has been down for about 7 hours.** It gives "No route to host"
   from both the LAN and f0. Knock-on effects:
   - zrepl `f0_to_f1_nfsdata` fails every minute
     (`dial tcp 192.168.2.131:8888: i/o timeout`), so the 2.25 TB of NFS data
     currently has no second copy.
   - CARP has no backup node; f0 is MASTER on its own.
   - k3s is running on 2 of 3 control-plane nodes, so one more failure loses
     quorum.
   - `prometheus-prometheus-kube-prometheus-prometheus-0` and
     `alertmanager-...-0` are stuck in `Terminating` on r1. StatefulSet pods
     never move off a node that stops responding on their own (they need a
     force-delete or a `node.kubernetes.io/out-of-service` taint), so the
     Prometheus stack has been down the whole time. The ArgoCD app
     `prometheus` shows Degraded.
   - Navidrome returns 503 publicly (its pod is Pending on
     `nodeSelector: r1`). Pods for about 15 other apps are stuck in Terminating
     on r1, though replacements seem to be running because only Navidrome
     shows as not ready.
   - I don't know why f1 went down. The JetKVM (on f1) or shelly2 are the next
     things to check.

2. **All f3s alerts are still muted.** `/tmp/f3s_taken_down` has existed on
   blowfish and fishfinger since 11:57. The cluster came back around 13:07,
   but my guess is that the `wol-f3s all` path waits for r0/r1/r2 to answer
   ping, r1 never did, and so `unmute_gogios` never ran. The result is that
   the f1/r1 Ping4/6, Navidrome HTTPS and "all Prometheus hosts failed" checks
   are all *suppressed*, and the report says `C:0`. In practice the mute stays
   on exactly when a host fails to come back. It should expire, or clear
   itself (and alert) when the wake times out.

3. **pi1's WireGuard is down.** `tun0` is not UP (`flags=0x50`), its address
   shows `DETACHED`, and `wg show` lists no peers. Gogios sees this over wg0
   (Ping4/6 and HTTP time out), but those checks are suppressed too (item 2).
   Nothing restarts it. pi0's tunnel is fine.

4. **Uncommitted typo breaks the gonf build.** At
   `gonf/frontends/monitoring.go:222`, the comment prefix `//` became `r/`,
   and `go build ./...` fails with `syntax error: non-declaration statement
   outside function body`. No recipe can deploy until it is reverted.

## High

5. **A cron job has filled root's mailbox on f0.** `/var/mail/root` is 120 MB,
   with about 203k cron mails from `carp-auto-failback.sh`.
   `/usr/local/bin/carp` runs `ifconfig -l | xargs -n1 | while … break`, which
   makes xargs print `xargs: /bin/echo: terminated with signal 13; aborting`
   every minute. Nothing reads root mail on any host (f2 also has about 3 MB of
   unread UPS mail), so real messages (UPS power failures, security runs) are
   buried as well.

6. **CARP auto-failback has a reliability problem.** On 2026-09-25 at 11:13 the
   log says "CONDITIONS MET: Promoting to MASTER (was INIT)" followed by
   "Failback complete: State is now BACKUP", so the promotion failed and
   nothing flagged it. `carp-auto-failback.sh` takes `awk '{print $NF}'` of the
   whole `carp` output, so the extra WARNING line printed when
   `nfs.NO_AUTO_FAILBACK` exists breaks the state detection.

7. **Stacked NFS mounts on r0 and r2.** `/data/nfs/k3svolumes` is mounted twice:
   the fstab `hard,timeo=600` mount with a `soft,timeo=50` mount from
   nfs-mount-monitor's `fix_mount` on top. The old mount is never cleaned up.
   Pods now write through a **soft** mount, including miniflux-postgres,
   immich-postgres and the Prometheus TSDB (a hostPath on NFS), and soft
   mounts can silently lose writes on timeout. The header of
   `f3s/r-nodes/nfs-mount-monitor/check-nfs-mount.sh` also says "mount
   timeo=10", which matches neither mount.

8. **Stateful apps are tied to r1, so r1 is a single point of failure.**
   Navidrome has `nodeSelector: kubernetes.io/hostname: r1.lan.buetow.org`
   (`f3s/navidrome/helm-chart/templates/deployment.yaml:43`) plus a
   `local-path` PVC (`navidrome-data-pvc`). The orphaned `storage-tempo-0`
   local-path PV is also bound to r1.

10. **ZFS scrubs have stopped.** The last scrub on every pool on f0, f2 and f3
    (zroot, zdata) was 2026-05-17, over four months ago.
    `daily_scrub_zfs_enable` is not set in periodic.conf.

11. **Gogios problems.**
    - The "Prometheus: Watchdog" check reads OK while Prometheus is
      unreachable, because it reports a stale state instead of failing.
    - The two reports disagree: fishfinger shows `SU:44`, `checksActive:false`
      and a stale "Check Disk fishfinger", while blowfish shows `SU:10`,
      `checksActive:true`. blowfish is currently the active checker despite
      `PeerPrimaryName: fishfinger`. `gogios.buetow.org` can serve either view.

## Medium

12. **UPS problems.**
    - On f2, apcupsd-over-network to f0 (`DEVICE f0.lan.buetow.org:3551`)
      keeps flapping: about 900 "Communications with UPS … lost/restored"
      mails.
    - f0's UPS shows `BATTDATE 2001-01-01` (never set), so there is no way to
      track battery age.
    - f0's apcupsd NIS server listens on `NISIP 0.0.0.0`.
    - Shutdown thresholds differ: f0 uses `BATTERYLEVEL 5` / `MINUTES 3`, f2
      uses 10 / 6. Check this is deliberate.

13. **Known vulnerabilities (`pkg audit`).**
    - f0: python311, python312, giflib, py311-setuptools, py312-setuptools.
    - f2: python311, python312.
    - f3: python312, plus 3 outdated packages.
    - pi0 and pi1: libxml2-2.15.1, perl-5.42.3.
    - Having both python311 and python312 installed suggests leftovers.

14. **Out-of-support versions.**
    - k3s is v1.32.6+k3s1, which is past upstream end of life.
    - cert-manager is v1.14.4, from 2024 and past end of life.
    - OpenBSD 7.8 on blowfish and fishfinger loses support when 8.0 ships
      around October/November 2026, so plan that upgrade now.

15. **bhyve VNC listens on all interfaces.** It is on `0.0.0.0:5900` on all
    f-hosts (and `:5901` on f0), presumably without a password. There is also a
    stale `fedora` VM on f0 stuck in `Locked (f0.lan.buetow.org)`.

16. **Leftovers from the disabled observability stack.**
    - PVC/PV pairs still exist for `grafana-data`, `loki-data` and `tempo-data`,
      plus the local-path `storage-tempo-0` on r1.
    - The Alloy DaemonSet still runs 3 pods with a no-op config and sends a
      usage report to Grafana Labs ("usage report sent with success").
    - `grafana.f3s.buetow.org` still resolves and returns 404 through relayd
      (TLS cert still issued), and Gogios is told to expect that 404.

17. **`f3s/argocd-apps/services/pihole.yaml` is still in the repo** but the app
    is not deployed, since Pi-hole moved to pi2/pi3 in Docker.

18. **Floating `:latest` or untagged images:** filebrowser, keybr, kosync,
    miniflux, protonbridge, radicale (local registry), syncthing,
    audiobookshelf, wallabag, and `pihole/pihole:latest` on pi2/pi3. Upgrades
    happen unpredictably whenever a pod restarts.

19. **About 30 workloads have no memory limit.**
    - services: anki-sync-server, audiobookshelf, filebrowser, immich-valkey,
      keybr, koreader-sync-server, miniflux-postgres, miniflux-server,
      navidrome, opodsync, protonbridge, radicale, syncthing, wallabag, webdav.
    - infra: docker-registry, pkgrepo.
    - cicd: argocd-application-controller, argocd-applicationset-controller,
      argocd-redis.
    - cert-manager: all three components.
    - monitoring: prometheus, alertmanager, operator, kube-state-metrics,
      node-exporter, alloy.

20. **No liveness or readiness probes** on ychat, opodsync, pushgateway,
    argocd-redis, argocd-applicationset-controller or cert-manager-cainjector.
    ychat is also known to be unresponsive, and Gogios skips it.

## Low / housekeeping

21. r0 and r2 root disks are 74% and 78% full, and containerd on r0 holds 38 GB
    across 206 images. Tighten image GC.
22. blowfish is at 79% on `/` with only 742 MiB free (Gogios is already
    warning).
23. Gogios checks only run 08:00–22:00 (`*/5 8-22 * * *`), so an overnight
    outage goes unnoticed until the morning.
24. Time zones are mixed: the Pis use UTC while the f-hosts and r-nodes use +03.
    Logs are harder to correlate.
25. The pi2/pi3 kernel is `6.1.31-v8.1.el9.altarch`, which is old. Check for a
    newer raspberrypi2 kernel. Both Pis also have pending dnf updates, and
    `needs-restarting -r` reports that both need a reboot.
26. 31 manifests under `f3s/` carry a meaningless `spec.ingressClassName`
    *annotation*; the real spec field is already set.
27. zrepl on f0 logs "callback channel is full, discarding snapshot update
    event".
28. firewalld is inactive on r0 and r2. Confirm that is intended, since the
    r-nodes rely on the frontends and WireGuard for protection.
29. pi0 has a WireGuard peer at `192.168.1.123:56709` (rocky) that has never
    completed a handshake (0 B received). Either configure it on rocky or drop
    it.

## Suggested order

1. Bring f1 back, lift the mute, and force-delete the stuck Prometheus and
   Alertmanager pods (items 1, 2).
2. Fix the mute-on-failed-wake logic (2), pi1's WireGuard (3), the typo (4),
   and the soft-mount stacking (7).
3. Stop the xargs/cron mail flood and route root mail somewhere it is read (5),
   then fix the CARP failback parsing (6).
4. Enable periodic scrubs (10) and decide on offsite backup for `zdata` and the
   etcd snapshots (9).
5. Work through the medium and low items.
