**Native Kubernetes reaches FreeBSD through experiments**

Investigated 15 October 2026. **Stock K3s does not support native FreeBSD, but a current experimental Kubernetes stack targets an ordinary FreeBSD 14.3-RELEASE host or VM.** Doug Rabson’s demo combines patched Kubernetes 1.36.1, a native kubelet, CRI-O and jail-backed containers. “Vanilla” therefore needs a distinction: the documented experiment uses the stock FreeBSD kernel, while its Kubernetes applications require patches and source builds. It is credible enough for an isolated proof of concept, but has no demonstrated production support or conformance certification. For this homelab, retain the existing Linux K3s guests for services and evaluate native FreeBSD separately. This investigation reviewed documentation and repository code; it did not deploy or test a cluster. ([K3s requirements](https://docs.k3s.io/installation/requirements), [FreeBSD Kubernetes demo](https://github.com/dfr/kubernetes-demo))

The available paths differ substantially:

| Path | Where pods execute | Assessment |
|---|---|---|
| Stock K3s, k0s or MicroK8s on FreeBSD | No documented native worker support | Changing distribution does not solve the platform gap. |
| Rabson’s patched Kubernetes demo | FreeBSD jails on the FreeBSD kernel | Best evidenced native experiment; source builds and manual integration required. |
| K3s inside Linux bhyve guests | Linux guest kernel | Practical established architecture, already represented in this repository. |
| Native control plane with Linux workers | Linux workers | Distinct from native FreeBSD workloads; packaged control-plane binaries alone are insufficient. |

K3s documents Linux and cgroups requirements; k0s documents Linux and Windows; MicroK8s expects a snapd-capable system or virtualization. None documents native FreeBSD support. Upstream Kubernetes documents Linux control planes and Linux/Windows workers. ([K3s](https://docs.k3s.io/installation/requirements), [k0s](https://docs.k0sproject.io/stable/system-requirements/), [MicroK8s](https://canonical.com/microk8s/docs/getting-started), [Kubernetes platforms](https://kubernetes.io/docs/setup/))

**Linuxulator does not turn FreeBSD into a stock Linux Kubernetes node.** The FreeBSD handbook identifies cgroups and namespaces as unsupported Linux system-management facilities. Native Kubernetes instead needs FreeBSD implementations of runtime, resource-control and networking behavior behind its interfaces. That is an engineering integration problem, rather than proof that Kubernetes must always use Linux. ([FreeBSD Linux compatibility](https://docs.freebsd.org/en/books/handbook/linuxemu/), [Kubernetes CRI](https://kubernetes.io/docs/concepts/containers/cri/))

The native demo is substantially more useful than older control-plane-only guides. It documents a single-node cluster and small multi-node experiments, with CNI bridges linked manually, for example using VLANs and distinct address-allocation ranges. It explicitly warns that its Kubernetes patches lack upstream review, endorsement and support. The checked FreeBSD ports for control-plane components still contain Kubernetes 1.27.2; these do not establish a current complete distribution, and that upstream minor release reached end of life in July 2024. ([Demo](https://github.com/dfr/kubernetes-demo), [API server port](https://raw.githubusercontent.com/freebsd/freebsd-ports/main/net/kube-apiserver/Makefile), [Release history](https://kubernetes.io/releases/patch-releases/))

**Treat the demo script as a build reference, not an installer for an existing server.** It assumes ZFS pool `zroot`, enables RACCT accounting with a boot tunable, installs Podman tooling, expects ocijail 0.6.0 or newer, loads kernel modules, and changes forwarding, filtering and startup configuration. It builds FreeBSD branches of CRI-O, kubelet and kubeadm and consumes control-plane images from `ghcr.io/dfr`. The script also assumes an amd64 crictl path, overwrites `kld_list`, and lacks fail-fast shell handling. Existing PF rules need deliberate integration. None of these observations establishes successful execution on your hosts. ([Build script](https://github.com/dfr/kubernetes-demo/blob/main/build-cluster.sh))

Start with **native FreeBSD OCI images**. FreeBSD joined OCI runtime specification 1.3 in November 2025, and official images are available. The Foundation also demonstrated selected Linux images under Podman/Linuxulator on vanilla FreeBSD 14.3 and 15.0-BETA3. That establishes some Linux userspace compatibility, but does not validate those images under this Kubernetes stack, arbitrary Helm charts, Linux privileged DaemonSets, standard CNI plugins or CSI drivers. ZFS-backed image storage likewise does not supply Kubernetes persistent-volume provisioning. ([OCI announcement](https://freebsdfoundation.org/blog/freebsd-officially-supported-in-oci-runtime-specification-v1-3/), [Foundation container tutorial](https://freebsdfoundation.org/blog/oci-containers-on-freebsd/))

There is active 2026 development: the demo advanced to Kubernetes 1.36.1 in June, with subsequent kubelet work in July. August Enterprise Working Group notes target an experimental Kubernetes port and build instructions by the end of 2026. **That is a roadmap target, not verified delivery or a support commitment.** ([Demo history](https://api.github.com/repos/dfr/kubernetes-demo/commits?per_page=8), [Kubelet history](https://api.github.com/repos/dfr/kubernetes/commits?sha=freebsd-kubelet-v1.36.1&per_page=3), [August meeting](https://lists.freebsd.org/archives/freebsd-enterprisewg/2026-August/000156.html))

Your configuration already expresses the practical bhyve route: FreeBSD f0–f2 host Rocky r0–r2, each configured with four CPUs and 12 GB RAM, and all three r-nodes participate in the K3s control plane. FreeBSD supplies CARP/relayd ingress and shared NFS storage; applications use hostPath volumes through the guests’ NFS mount. These are repository findings, not live-state verification. Removing Linux would therefore require validating those workload, ingress and storage integrations as well as booting Kubernetes. ([VM inventory](/home/paul/git/conf/gonf/cluster/freebsd_bhyve.go:5), [K3s recipe](/home/paul/git/conf/gonf/rnodes/k3s.go:9), [Ingress](/home/paul/git/conf/gonf/freebsd/relayd.go:9), [NFS client](/home/paul/git/conf/gonf/rnodes/nfsclient.go:9))

My recommendation is one disposable **FreeBSD VM** with ZFS, console access, a snapshot and a separate network. This still tests native FreeBSD workers; bhyve only isolates the experiment. Inspect and adapt the demo before running it. Proceed beyond single-node evaluation only after native pods survive creation/deletion, Deployment updates and reboot; DNS, Services and egress work; resource limits demonstrably apply; and persistent data survives pod replacement with correct permissions. Stop migration planning if required applications, storage drivers or networking cannot pass these checks. Multi-node routing, node failure and upgrade/rollback need their own successful exercises before replacing any existing service. The immediate opportunity is to establish which of your workloads FreeBSD can host natively, with the current K3s environment preserved throughout.
